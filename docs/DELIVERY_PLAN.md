# 개발 순서와 완료 조건

**구현 기준:** 방장의 공유 확인과 각 차량의 목적지 변경 확인이 매번 필요하다. 이전 자동 따라가기 동의로 내비를 쓰지 않는다. 현재 화면·동작은 [REVIEW_02](REVIEW_02.md)와 [IMPLEMENTATION](IMPLEMENTATION.md)을 따른다. 나머지 확장 설계는 구현 완료를 뜻하지 않는다.

현재 0.3에서 M0~M2 중 여행방·두 차량 목적지 등록·위치/ETA의 작은 완결 흐름을 구현하고 두 독립 SDK 에뮬레이터에서 확인했다. 실제 완료·검증 범위는 [IMPLEMENTATION](IMPLEMENTATION.md)과 [VERIFICATION](VERIFICATION.md)을 따른다. 아래 전체 수용 기준이 모두 통과했다는 뜻은 아니다.

사용자 관점 보정은 REVIEW_01.md를 따른다. 아래는 앞으로 앱에서 실행할 수용 기준이며, 설계 참고 모델의 통과와 구분한다.

## M0 공개 SDK 연결 시험

가장 먼저 작은 연동 화면으로 핵심 가능성을 확인한다.

1. NaviHelper 연결과 현재 목적지·경유지·ETA·POI 전체 필드 기록.
2. 순정 내비에서 읽은 장소를 같은 차량에 다시 요청하고 실제 readback 일치 확인.
3. 목적지와 경유지 0/1/2개, poiSubId null/빈 값/원래 값, 공급원 차이의 성공·실패 표 작성.
4. FusedLocation 지원·허용·수신 간격·null·단절·timestamp 의미 확인.
5. 내비 옆 좁은 윈도우, 넓은 윈도우, 백그라운드 전환에서 연결 지속 확인.
6. TTS ON_DEVICE 한국어·오디오 포커스, 지도 렌더러의 에뮬레이터 표시 확인.
7. 정상 경유지 통과·수동 삭제·경로 옵션만 변경·안내 취소의 콜백과 재조회 차이 확인. 도착 이벤트의 인덱스를 당시 적용 경로에 매핑.
8. 내비 요청 시간 초과·늦은 완료·이전 요청 종료 확인 방법을 조사. 방법이 없으면 시간 초과 후 자동 쓰기 중단을 유지.
9. 현재 목적지가 이미 있는 상태의 방 생성, ETA 갱신 주기, 좌표/POI 정규화, 서버 HTTPS 접속 확인.

**통과 기준:** 실제 SDK 입력과 요청 결과 로그, 각 API별 성공/제약이 있는 표. 호출만 하고 성공 표시한 화면은 통과가 아니다. 지원하지 않는 장소 조합은 자동 반영 대상에서 제외한다. 차량 위치와 동기화의 핵심이 미지원이면 그 사실을 먼저 반영해 설계를 보정한다.

## M1 방과 제어 계약

- 서버 세션, 여행방·초대, 위치·ETA 공유 선택과 변경별 목적지 확인.
- 방장 계획과 차량별 개인 계획, idempotency·버전 충돌 처리.
- snapshot+WebSocket, 재연결·만료·방 종료.
- 3개 fixture 클라이언트로 목적지 변경, 개인 픽업 보존, 지연·중복 사건 검사.
- 초기/늦은 합류 snapshot, 잘못된 동의 조합, StopDecision·VisitProgress·명시적 경유 순서, 개인 종료/전체 종료 분리.
- 공용 방 snapshot에서 개인 경유지·승객 위치를 제거하는 실제 서버 권한 검사.

**1차 보정:** 확인한 목적지가 등록되는 흐름, 방장 화면의 차량별 상태, 동의 화면이 번거롭지 않은지 확인한다.

## M2 차량용 앱의 핵심

- 앱 ID `dev.moa.trip`, 주행 제한·권한 처리, Room 저장.
- T01~T05 및 T09: 방 참여, 여행 패널, 자체 지도, 공동 경유지, 동기화 확인.
- M0에서 확인한 범위의 실제 SDK 어댑터 연결.
- 먼저 두 차량의 목적지 반영과 위치/ETA 카드가 연결되는 작은 완결 흐름을 만든다. 지도 상세·스티커·음성이 이 통과 조건을 막지 않게 한다.
- 내비 재탐색과 목적지 변경을 구분하고 실제 차량별 ETA를 읽는다.
- 최소 2개의 독립 클라이언트로 검증한다. 메모리 때문에 SDK 기기 1대+fixture만 쓴 결과는 복수 SDK 차량 검증으로 표시하지 않는다.

**2차 보정:** 좁은 화면 우선순위, 일행 ETA·위치 가독성, 휴게소 건너뛰기와 개인 경유지 충돌을 확인한다.

## M3 여행·픽업 통합

- 프리셋·스티커, 휴식 요청 이유 집계, 도착·출발 준비.
- 동승자 웹, 픽업 승객 링크와 제한된 세션.
- 후보 비교 계산·실제 자동차/보행 공급자 어댑터·사용량 상한.
- 검토된 지역의 실제 후보, 승객 동의, 해당 차량에만 내비 반영.
- 확정된 만남 장소 고정, 내비 반영 전 출발 안내 차단, 걷는 부담 대비 절감 기준, 취소/변경 합의.
- 도착 후 만남 핀과 입구 설명. 핀 게시만으로 모든 차의 내비를 다시 바꾸지 않는다.

**3차 보정:** 픽업 화면에서 걷기와 절감 이득을 한 번에 이해하는지, 친구 기능이 여행 조율을 방해하지 않는지 확인한다.

## M4 완성 검증과 배포 준비

- 네트워크 중단, SDK 재연결, 프로세스 종료, 권한 철회, 오래된 ETA, 방장 양도, 초대 만료 검증.
- release 서명, 설치·실행 안내, 에뮬레이터 버전·화면 규격·외부 키 설정 구분.
- 소스·APK·운영 설정에 비밀키와 승객/차량의 실제 위치 기록이 들어가지 않는지 점검.
- 서버 없는 상태의 기능 표시와 시연용 입력 앱을 분명하게 구분.

**이후:** 앱이 완성되고 보정을 거친 뒤 별도 GitHub 저장소를 만든다. 시연 영상은 그 다음 단계다. 현 단계에서는 생성·업로드·촬영하지 않는다.

## 외부 준비물

초기 설계·계산과 fixture 구현에는 외부 계정이 필요 없다. 실제 연결 단계에서 TMAP 경로 API 키, 지도 스타일/타일 공급, 휴대폰이 접속할 HTTPS 서버가 필요하다. 계정·유료 서버는 자동으로 개설하지 않는다. 해당 준비가 없더라도 여행방 서버와 차량 앱의 독립 구현은 진행할 수 있다.

## 최초 설계 자체 보정 기록

1. 초기 방 단위 자동 동기화 설계는 폐기했다. 현재 구현은 최신 사용자 요청에 따라 매 변경마다 방장과 각 차량이 확인한다.
2. 공동 목적지와 개인 픽업을 나눠 한 차량의 픽업이 전 차량 경유지가 되는 문제를 막았다.
3. 내비 쓰기 API가 있어도 POI·권한·readback 검증이 필요하므로 M0를 가장 앞에 뒀다.
4. ‘서버 전달 성공’과 ‘각 차량 내비 반영 완료’를 별도 상태로 정리했다.
5. 위치와 ETA 신선도, 픽업 대기 시간 중복 계산, 외부 호출 상한을 명시했다.
