# 사용자 관점 검토와 수정

2026-11-13. 방장, 참가 운전자, 동승자, 픽업 승객 입장에서 첫 참여부터 귀가 전 종료까지 가상 상황을 따라 검토했다. 실제 사용자 인터뷰·주행 테스트 결과가 아니다. 아래 ‘수정’은 제품 명세·데이터 계약·계산 규칙의 수정이며 앱 구현 완료를 뜻하지 않는다.

## 중요한 판단

핵심 아이디어는 유지한다. 목적지를 다시 입력하지 않고, 전화 없이 다음 만남과 일행 상태를 맞추며, 픽업까지 같은 여행 흐름에서 해결하는 가치가 있다. 반면 두 번째 지도를 계속 바라보거나 이모티콘을 많이 보내는 것만으로는 주행 중 사용할 이유가 약하다. 기본 화면을 다음 만남과 차량별 상태로 좁히고 지도·스티커는 보조 화면으로 정리했다.

## 찾은 문제와 수정

| ID | 사용자 입장에서 드러나는 문제 | 반영한 수정 |
|---|---|---|
| R01 | 목적지를 먼저 찍고 방을 만들면 변경 이벤트가 없어 빈 방이 됨. 늦게 들어온 차도 다음 변경까지 대기 | 생성 시 현재 목적지 확인, 입장·복귀 시 최신 계획 조회 |
| R02 | 동의 스위치 4개만 있으면 무엇을 켜야 할지 모름 | 함께 길 안내/내 경로 선택과 실제 변경 미리보기, 공유 선택은 명시적으로 유지 |
| R03 | 목적지 따라가기는 껐는데 경유지만 동기화하다 최종 목적지까지 바뀔 수 있음 | 잘못된 동의 조합 거부, 따라가기 해제 시 공동 자동 반영도 해제 |
| R04 | 내비에서 자연스럽게 사라진 방문 완료 경유지를 수동 변경으로 오해하거나 재접속 때 다시 넣음 | 차량별 방문 회차·완료 상태, 정상 진행과 수동 편집 분리 |
| R05 | 서로 다른 길에서 이미 지나쳤거나 반대 방향인 휴게소로 자동 재탐색 | 출발 전 합의/주행 중 새 제안 분리. 새 휴게소는 각 차의 들르기/직행 선택 |
| R06 | 3대 중 1대가 끊겼는데 나머지 2대의 ETA를 ‘모두 모일 시각’으로 표시 | 전체 참여 분모, 누락·미정 수, 전체 확인 시에만 집결 예상 표시 |
| R07 | 먼저 도착한 방장이 ‘종료’를 눌러 뒤차와 걷고 있는 승객까지 방에서 끊음 | 개인 종료와 전체 종료 분리. 전체 종료 전 진행 중 차량·픽업 확인 |
| R08 | 승객이 걷자 50m 이동 조건이나 90초 만료로 다른 장소가 다시 추천됨 | 확정 전 추천 TTL과 확정 후 만남 분리. 합의 장소 고정 |
| R09 | 승객에게 출발하라고 했지만 운전자 내비에는 장소가 반영되지 않음 | 반영 확인 전 대기 문구, 유효한 차량 안내 확인 후 출발 안내 |
| R10 | 승객에게 많이 걷게 하면서 실제 단축은 작음. ‘걷지 않기’도 0초 후보를 추천할 수 있음 | 절감 2분 이상이며 보행 시간 이상인 안만 기본 추천, 걷지 않기면 대안 추천 중지 |
| R11 | 내비 요청 시간 초과 뒤 다음 요청을 보냈다가 이전 요청이 늦게 덮어씀 | WRITE_UNCERTAIN에서 추가 쓰기 차단, 실제 종료 확인 전 재시도 금지 |
| R12 | 방장이 개인 용무로 내비를 바꾸거나 안내를 끝내면 전원에게 잘못 전파 | 목적지 공유 일시중지/재개, 안내 취소와 공동 계획 삭제 분리 |
| R13 | 캠핑장→식당으로 바꿨는데 이전 방향의 휴게소가 남거나 픽업 앞뒤가 임의 결정 | 남은 공동 장소 유지/정리 확인, 개인·공동 경유 순서 명시, 확정 픽업 보존 |
| R14 | 순정 내비와 여행 지도 두 개를 읽느라 정작 필요한 정보가 안 보임 | 좁은 화면은 다음 만남·고정 순서 차량 카드 중심. 지도는 펼쳐서 확인 |
| R15 | 준비한 두 대만 세어 ‘모두 준비’라거나, 새로 온 차가 이전 READY 상태를 이어받음 | 방문 회차·참여 인원·신선한 확인 기준, READY 10분 후 재확인, 미정/미도착 별도 |
| R16 | 운전자와 동승자가 같은 휴식 요청을 눌러 차량 수가 부풀고 음성이 연달아 울림 | 차량별 중복 제거·10분 만료·철회. 남의 적용 성공과 스티커는 TTS 기본 제외 |
| R17 | 일반 방 조회에 승객 좌표·개인 경유지가 섞이거나 방 위치 공유를 꺼 픽업도 못 함 | 방/픽업의 동의 범위 분리, 서버 응답 필드 제한, 승객에게는 차량 접근 ETA |
| R18 | 초대 링크를 한 번 쓰면 새로고침도 안 되거나 방 연장으로 위치 공유까지 계속됨 | 여러 차량용 방 코드와 1회 교환 웹 초대 구분, 웹 세션 유지, 연장 시 개인 동의 기간 유지 |
| R19 | 같은 주소에 도착했는데 서로 다른 주차장·입구에서 기다림 | 기존 지도 위의 만남 핀·입구 설명을 작은 확장으로 추가, 안내 변경은 별도 동작 |
| R20 | 동승자·음성·스티커부터 만들다 실제 목적지 동기화의 성패가 뒤늦게 드러남 | 첫 동작 범위를 방 참여→두 차량 목적지 반영→위치/ETA로 고정 |

R05의 휴게소 참여 확인, R10의 이득 기준, R15의 준비 만료는 자체 제품 판단이다. 현대가 정한 의무 조건으로 표시하지 않는다. 픽업 후보의 진입 가능성, SDK 비동기 종료, 운전 중 허용 조작은 실연동 검증이 남아 있다.

## 보정한 대표 화면

```text
양평 캠핑 여행                 3대
다음 만남  ○○휴게소            들르기 2 · 직행 1
A   약 14:08                   안내 반영
B   연결 확인 중               마지막 갱신 25초 전
C   픽업 중                    다음 만남 건너뛰기
집결 시각 확인 중              참여 2대 중 1대 확인
```

오래된 차량은 지도 마커를 계속 움직이지 않지만 목록에서 사라지지도 않는다. 도착 시간순 순위를 매번 바꾸지 않는다. 위 수치는 화면 설명용 가상 값이다.

```text
픽업 승객 화면
만남 장소  ○○역 2번 출구 앞 지정 지점
장소 합의 완료 · 차량 안내 확인 중
아직 출발하지 마세요

차량 안내 확인 후
만남 장소 그대로 · 도보 약 3분
권장 출발 시각 14:02            계산 시각 표시
[이제 출발해요] [장소 변경 요청] [픽업 취소]
```

확정 장소를 변경할 때는 양측이 새 장소에 합의하고 새 내비 반영 상태를 확인한다. 이동 중 위치 변화는 기존 장소의 남은 시간 갱신에 사용한다.

## 추가/확장의 우선순위

1. 첫 완성에 포함: 진행 중 방 복귀, 늦은 합류, 참여/직행/미정, 집결 인원 표시, 확정 픽업, 만남 입구 메모.
2. 핵심 검증 뒤: 동승자 웹·짧은 음성 요청·프리셋 확장.
3. 후속 검토: Pleos가 없는 차의 휴대폰 참여. 실제 여행에서는 차종이 섞일 수 있다. 일반 휴대폰에 순정 내비 자동 등록이나 NaviHelper ETA가 있는 것처럼 표시하지 않고 별도 참여 유형·능력을 설계해야 한다. 첫 버전은 Pleos 차량 중심이라는 제약을 명시한다.
4. 후속 검토: 사전 지정 대체 방장. 현재는 방장 단절에도 기존 안내가 유지되지만, 새 공동 계획 게시 권한은 자동으로 이전하지 않는다.
5. 보류: 전체 채팅, 속도·도착 경쟁, 예약·결제, 다수 승객 자동 배차. 첫 여행 경험 검증을 지연시키는 범위 확장은 넣지 않는다.

## 검증 범위

계산 예제와 사용 시나리오의 기대 결과를 contracts에 고정하고, tools/verify_design.py로 검사한다. 상태 규칙은 tools/design_model.py의 설계 참고 모델로 검토한다. 이 도구는 차량 앱·서버 구현이 아니며 SDK 성공을 증명하지 않는다. 실제 기기 수용 시나리오는 DELIVERY_PLAN.md에 추가했다.

이전 문서는 work의 설계 보관 폴더에 보관했다. 검토 내용은 PRODUCT, ARCHITECTURE, PICKUP, SDK_EVIDENCE, DELIVERY_PLAN과 product-policy에 반영했다.
