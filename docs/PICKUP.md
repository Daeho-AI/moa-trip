# 여행방에 통합하는 픽업

v0.2 · 추천 단계와 확정 후 만남 단계를 분리한다.

## 1. 핵심 경험

‘B 차량이 친구를 태운 뒤 여행 목적지로 간다’는 상황을 처리한다. 승객이 허용하는 범위에서 걸어 나올 수 있는 장소를 비교하고, 걷는 부담과 최종 목적지까지의 예상 절감 시간을 함께 보여준다. 가장 가까운 차량 픽업점만 찾는 기능이 아니다.

메뉴는 `여행방 → 내 차량 → 픽업 추가`다. 운전자는 기존 경유지 중 사람을 태울 곳을 선택하거나 검토된 장소를 원래 픽업점으로 선택한다. 승객 링크를 만들고 현재 위치, 준비 시간, 허용 도보를 받는다. 승객은 위치 권한 대신 수동 핀도 사용할 수 있으며 입력 출처를 표시한다.

최초 범위: 차량당 활성 픽업 1건·승객 1명·대안 최대 6곳. 방의 다른 차량은 같은 픽업 지점을 경유하지 않는다. 해당 차량의 PersonalPlan만 바뀌며, 다른 차량에는 ‘픽업 중’ 상태만 보인다. 공동 장소와의 경유 순서는 미리 확인한다. 픽업 전에 예정된 휴식 시간이 불명확하면 정밀한 추천 대신 ‘휴식 후 다시 비교’를 안내하거나 픽업을 먼저 하는 순서를 선택하게 한다.

## 2. 계산

같은 계산 기준 시각 t0에서 다음 값을 구한다.

- A(Q): 차량 현재 위치에서 앞선 경유지들을 거쳐 후보 Q까지 자동차 소요 시간.
- W(Q): 승객 현재 위치에서 Q까지 실제 보행 소요 시간.
- B(Q): Q에서 뒤의 경유지들을 거쳐 최종 목적지까지 자동차 소요 시간.
- R: t0부터 승객이 출발 준비를 끝내기까지 남은 시간.
- S: 탑승 소요 시간. 초기 기본값 60초.

```text
meeting(Q) = max(A(Q), R + W(Q))
driverWait(Q) = max(0, R + W(Q) - A(Q))
passengerWaitIfLeavingWhenReady(Q) = max(0, A(Q) - R - W(Q))
total(Q) = meeting(Q) + S + B(Q)
saving(Q) = total(originalPickup) - total(Q)
suggestedWalkStartAfter = max(R, A(Q) - W(Q))
passengerWaitAtSuggestedStart = max(0, A(Q) - suggestedWalkStartAfter - W(Q))
```

meeting에서 이미 대기를 반영했으므로 driverWait를 total에 다시 더하지 않는다. 준비 완료 시각은 절대 시각으로 저장하고 재계산 때 이미 지난 준비 시간을 다시 더하지 않는다. 자동차·보행 시간은 동일 공급원과 가까운 시각의 응답으로 비교한다. 현대 내비의 기준 시간에서 TMAP 대안 시간을 빼지 않는다.

계산은 주행·걷기·대기·탑승을 비교하는 예상이다. 계획에 없는 식사·휴식이나 픽업 이후 미래 교통을 정확히 보장하지 않는다. 최신 순정 내비 ETA와 외부 계산의 절감 예상은 다른 항목으로 표시한다. ‘준비되는 대로 바로 나갔을 때 대기’와 ‘권장 출발 시각에 맞췄을 때 대기’를 구분한다. 권장 시각은 화면상의 참고이며 웹이 닫힌 상태의 알람 전달을 보장하지 않는다.

## 3. 후보와 순위

1. 차량 진입, 보행 접근, 같은 입구에서 만남 가능 여부와 순정 등록을 검토한 후보를 쓴다.
2. 승객 주변 후보 최대 6곳과 원래 픽업점 하나를 비교한다. 직선거리는 후보 축소에만 사용한다.
3. 실제 자동차/보행 경로가 없거나 계산이 오래되면 제외한다.
4. 허용 도보 기본 3분(걷지 않기/3/5/10분 선택), 차량 대기 기본 상한 2분을 적용한다. ‘걷지 않기’는 대안 추천을 끄고 원래 만남 장소를 유지한다. 위치 오차 때문에 보행 시간이 0인 다른 핀을 새 장소로 추천하지 않는다.
5. 기본 추천에는 기준 대비 2분 이상 절감하면서 절감 시간이 보행 시간 이상인 후보만 넣는다. 10분 걷고 2분 줄이는 안을 가장 좋은 선택으로 밀지 않는다. 이는 제품 초기 추천 기준이며 보편적인 최적 비율이라고 주장하지 않는다. total → walk → driverWait → id 순으로 상위 3개를 표시한다.
6. 후보가 없으면 원래 장소를 유지한다. 기준 계산 자체가 실패하면 절감 시간을 만들지 않는다. 일부 후보 조회만 실패하면 비교 성공 후보 수를 표시한다.

주소가 가깝더라도 반대편 도로·다른 출입구·차량 진입 불가·횡단 불가이면 같은 만남 지점으로 취급하지 않는다. 길찾기 성공만으로 승하차 장소가 적합하다고 보증하지 않는다. 초기 시연 지역의 검토된 후보로 시작하며 전국 자동 최적을 주장하지 않는다.

## 4. 선택과 동의

```text
DRAFT → INVITED → INPUT_READY → COMPARING → OPTIONS_READY
OPTIONS_READY → PASSENGER_ACCEPTED → DRIVER_CONFIRMED
DRIVER_CONFIRMED → APPLYING → APPLIED → MEETING → BOARDED
```

어느 단계든 CANCELLED/EXPIRED가 될 수 있다. **DRIVER_CONFIRMED 전**에는 계획 변경·이동·추천 유효시간 초과를 NEEDS_RECALCULATION으로 처리한다. 이후에는 만남 장소를 MeetingCommit으로 고정한다. 90초가 지났거나 승객이 50m 걸었다는 이유로 확정 장소를 무효화하거나 다른 곳을 추천하지 않는다.

승객 동의는 candidateId, candidateSetVersion, maxWalkSec, 만남 좌표와 연결한다. 최종 확정은 배정된 운전자가 한다. 확정 직전 원래 장소와 선택 장소를 다시 계산하고 공동/개인 계획 버전을 검사한다. 승객이 동의한 장소·보행 조건이 달라지면 다시 동의받는다. 확정 직전 리더가 목적지를 바꾸었다면 옛 추천을 확정하지 않는다. 확정 후 리더 목적지가 바뀌면 만남 장소를 보존하고 이후 경로와 ETA만 갱신한다.

픽업 변경은 해당 차량의 경유지 자리만 교체한다. 공동 경유지와 합해 2개를 넘으면 저장만 해 놓고 반영했다고 표시하지 않는다. 운전자에게 전체 경유 순서를 보여주고 정차 후 조정하게 한다. 다른 차량에 픽업 경유지를 전파하지 않는다.

승객 화면은 APPLYING/WRITE_UNCERTAIN/FAILED에서 ‘차량 안내 확인 중 · 아직 출발하지 마세요’를 표시한다. 내비 반영이 확인되고 차량 상태도 최신일 때 확정 장소와 권장 출발 시각, ‘이제 출발해요’를 제공한다. 예상 출발 시각이 미래면 지금 걷도록 재촉하지 않는다. 앱은 사람의 실제 출발을 강제할 수 없으며, 출발 버튼이 도착 시각을 보증하지도 않는다.

확정 후 이동은 같은 장소로 향하는 남은 시간 갱신에만 사용한다. 장소 변경은 별도 제안→승객 재동의→운전자 재확정→해당 내비 적용 확인을 거친다. 새 합의 전에는 기존 장소가 계속 기준이다. 새 장소 적용이 불명확하면 이전/새 장소 중 임의로 ‘이곳으로 오세요’를 고르지 않고 확인 상태를 양측에 알린다.

탑승 완료는 해당 운전자가 확인한다. 근접 위치나 경유지 도착만으로 탑승을 추정하지 않는다. 완료 즉시 승객 위치 공유와 초대 접근을 종료한다. 승객 또는 운전자가 취소하면 상대에게 취소 상태를 전달하고 새 이동 안내를 중단한다. 오프라인 상대에게 이미 전달됐다고 표시하지 않는다. 취소한 픽업 경유지 제거도 실제 내비 확인 전에는 완료라고 표시하지 않는다.

## 5. 카드에 표시할 내용

| 항목 | 예시 문구의 의미 |
|---|---|
| 승객 도보 시간·거리 | ‘3분 · 210m 걷기’ — 실제 보행 응답 |
| 픽업 후 최종 도착 예상 | 전체 계산 결과. 미래 교통 예측 보증 아님 |
| 원래 장소 대비 예상 단축 | 같은 공급원·시점 기준의 차이 |
| 차량·승객 예상 대기 | 즉시 출발/권장 출발 기준을 구분. 권장 시각 전에는 기다렸다 나올 수 있음을 안내 |
| 만남 지점 | 출입구/진입 방향/확인할 표식 |
| 계산 시각·입력 출처 | 실시간 위치 또는 수동 핀, 공급원 |
| 동의·적용 상태 | 승객 동의 / 운전자 확정 / 내비 반영을 구분 |

‘도보 3분으로 약 8분 단축’은 계산 예제에서 가능한 결과이며 고정 광고 문구로 실제 결과에 넣지 않는다.

## 6. 외부 호출과 유효기간

- 자동차 `POST https://apis.openapi.sk.com/tmap/routes`, 보행 `POST https://apis.openapi.sk.com/tmap/routes/pedestrian`.
- WGS84GEO, 경도 X·위도 Y 순서, appKey는 서버에만 둔다.
- 입력/결과는 `RoutingProvider.drive/walk` 인터페이스로 정규화한다. 특정 공급원의 지도 ID는 NativeBinding과 분리한다.
- 첫 비교 정상 호출 최대 21회, 재시도 포함 HTTP 시도 최대 24회. 최종 2곳 재검사는 정상 호출 최대 6회·전체 시도 최대 8회.
- 동시 호출 3개, 개별 5초 제한, 작업 45초 제한. 429에는 자동 재시도하지 않는다. 전체 예산 안에서 일시 네트워크 오류만 1회 재시도한다.
- 기본 서버 일일 경로 호출 시도 상한 300회. 유료로 자동 전환하거나 상한을 자동 올리지 않는다.
- **확정 전 추천 결과**는 90초, 경로 응답 캐시는 동일 입력에 60초 사용한다. 위치·옵션·경유지 순서·공급원이 캐시 키에 포함된다.
- 확정 전 차량 250m·승객 50m 이동 또는 계획 변경 시 기존 추천을 재계산 필요로 표시한다. 실제 호출은 비교/갱신 요청 시에만 하며 GPS마다 자동으로 새 후보 6개를 조회하지 않는다. 동시 비교 요청은 같은 작업으로 합친다.
- 확정 후 같은 장소의 접근 ETA는 우선 차량의 해당 경유지 NaviHelper 값을 이용한다. 승객 보행 재조회는 사용자가 요청하고 한도 안에 있을 때만 한다. 권한 거부·오래된 위치에는 수동 확인 위치와 시각을 표시한다.
- 키가 없거나 한도에 도달하면 직접 지정 픽업과 동의 흐름은 유지하고 ‘시간 비교 연결 필요’를 표시한다. 직선거리로 절감 시간을 꾸며 넣지 않는다.

## 7. 계산 검토 예제

다음은 실제 도로 결과가 아닌 설계 검증용 수치다. 준비 0초, 탑승 60초, 허용 도보 180초 기준.

| 후보 | 차량 접근 | 보행 | 픽업 이후 | 총시간 | 절감 | 판정 |
|---|---:|---:|---:|---:|---:|---|
| 원래 장소 | 600 | 0 | 1200 | 1860 | 0 | 기준 |
| A | 300 | 180 | 1020 | 1380 | 480 | 1위 |
| B | 120 | 240 | 960 | 1260 | 600 | 걷기 한도 초과 |
| C | 400 | 120 | 1100 | 1560 | 300 | 2위 |
| D | 120 | 120 | 1500 | 1680 | 180 | 3위 |

걷기 허용을 300초로 늘리면 B가 1위다. 데이터는 `contracts/pickup-examples.json`에 저장했다.
